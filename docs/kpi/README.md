# Engineering Standards Compliance Matrix

The engineering standards this matrix tracks are a **spec-review rubric**, not measured KPIs: they list what every Engineering Spec and every build must already answer. This document splits the rubric into 36 checkable standards, adds 16 the rubric never asks for but this boilerplate already ships, ranks all 52 P0–P3, and records where this repository stands on each.

> **Scope note (23 October 2026):** this repository is adapted for TradeScope.
> The `@app/grpc` and `@app/storage` packages were removed, the leftover `note`
> domain was deleted, the main branch was aligned to `main`, and the database/cache
> runtime uses Neon serverless + Upstash Redis (the node-postgres/ioredis drivers
> remain available for local and CI). Matrix rows that still mention storage, gRPC,
> or notes are historical notes and no longer describe this repository.

## How to read this

**★ marks a standard the external rubric does not list.** Those 16 rows are what this boilerplate contributes on its own, and they are why the rubric rows that are Done were cheap rather than expensive.

**Severity is the criticality of the standard itself**, not of our status: a P0 stays P0 whether we pass it or not, so `P0` + `Missing` is what to fix first. The legend is the one in `.github/PULL_REQUEST_REVIEW_TEMPLATE.md`.

| Severity | Meaning |
|----------|---------|
| P0 | Blocker: data loss, security hole, full outage, or an external action taken wrongly |
| P1 | High: significant incorrect behavior, or a handoff gap that stalls operations |
| P2 | Medium: misleading UX, missing coverage, unbounded growth |
| P3 | Low: cleanup and polish |

| Status | Meaning |
|--------|---------|
| Done | Met in the repository today, with evidence |
| Partial | Mechanism exists but is incomplete or unenforced |
| Missing | Not present |
| N/A | Not exercised by the current codebase; required the moment the capability lands |

**Type** answers whose desk a standard lands on when it is not met. It is orthogonal to severity: a P0 can be a business decision and a P3 can be code.

| Type | Meaning |
|------|---------|
| Technical | Closed by writing code, configuration, schema, or tests |
| Business | Closed by a decision or data the business owns: a definition, a unit, a taxonomy, what counts as correct |
| Project | Closed by a project activity: running a procedure, naming an owner, recording a walkthrough, provisioning an environment |

**The Business rows are the PM's, and they are tracked outside this repository.** This repository is the technical half of the rubric. A standard that is closed by a definition, a unit, an approved taxonomy, or a rule about what counts as correct cannot be closed by a commit, and the material that would close it is product-specific, so it belongs in the PM's own documentation rather than in a neutral boilerplate. All five Business rows sit in that state. They stay listed here because deleting them would hide a real gap from anyone reading this matrix, but nothing in this repository will move them, and their status should be read as pending elsewhere.

**Boilerplate Ready** answers what a new product built on this repository inherits, which is a different question from whether this repository meets the standard.

| Boilerplate Ready | Meaning |
|-------------------|---------|
| Yes | Inherited for free: generic, wired up, nothing product-specific to finish |
| Partial | The reusable part exists; the product finishes the standard on top of it |
| No | Nothing to inherit, so the next product builds this from scratch |

The rubric's domain examples (Drive filing, CSI terminology, rebid ambiguity) come from a document-filing product. This repository is a full-stack boilerplate with no AI model and no filing workflow, so those rows are N/A with the condition that makes them apply.
